# STE Korean: 용어와 문장 패턴

모든 예시는 이 패키지를 위해 작성했다. 실제 장비나 서비스의 동작 설명이 아니다.
이 파일은 기본 규칙을 보충한다. 특정 프로젝트의 확인된 정의를 우선한다.

## 1. 용어 목록의 범위

영어 STE 사전을 한국어로 번역한 목록이 아니다.
문서에서 혼동하기 쉬운 개념과 반복되는 기술 용어를 관리하는 작은 용어 목록이다.
모든 한국어 단어를 열거하거나 목록 밖 단어를 일괄 금지하지 않는다.

필요한 정보는 개념 식별자, 대표 용어, 정의, 범위, 근거와 상태다.
한 문서의 임시 결정과 조직의 공식 승인을 구분한다.
기존 용어집과 충돌하면 새로운 표현을 자동 승인하지 않는다.

### 예제 용어 목록

아래 정의는 예제 문서 안에서 사용하는 정의다. 실제 프로젝트에 자동 적용하지 않는다.

**identity-check — 인증**

정의: 요청자가 제시한 신원을 확인하는 과정.
자원 사용 권한의 판정과 구분한다. 상태: 예제 정의.

**permission-check — 인가**

정의: 특정 자원을 사용할 권한이 있는지 판정하는 과정.
신원 확인과 구분한다. 상태: 예제 정의.

**write-config — 설정 저장**

정의: 편집한 설정을 설정 파일에 기록하는 작업.
서버에 설정을 적용하는 작업과 구분한다. 상태: 예제 정의.

**apply-config — 설정 적용**

정의: 저장된 설정을 서버의 동작에 반영하는 작업.
설정 파일을 기록하는 작업과 구분한다. 상태: 예제 정의.

### 한국어 활용

대표 동사가 `저장하다`이면 `저장하십시오`, `저장하면`, `저장했습니다`를 문맥에 맞게 쓸 수 있다.
`저장됨`이라는 상태명과 `저장하다`라는 행동을 같은 문장 역할로 취급하지 않는다.
명사형이나 활용형을 탐지했다고 곧바로 비승인 용어로 판정하지 않는다.

문서의 실제 UI 이름이 `Save changes`이면 해당 표기를 유지한다.
본문에서 작업 개념을 설명할 때는 확인된 한국어 대표 용어를 쓴다.
UI 문자열을 용어 통일의 대상으로 삼아 자동 번역하지 않는다.

### 신규 용어 처리

이미 쓰는 용어와 뜻이 같으면 기존 대표 용어를 사용한다.
뜻이 다르면 별도 개념으로 기록한다. 뜻이 불분명하면 원문을 유지하고 확인한다.
조직의 승인 절차가 없으면 `문서 내 임시 용어`로만 사용할 수 있다.
임시 용어가 핵심 작업의 해석을 결정한다면 확정된 실행 절차로 제시하지 않는다.

## 2. 행동과 설명의 분리

이 예제의 근거 정보:

`운영자는 설정 파일을 저장한 다음 서버를 다시 시작해야 한다.`
`서버는 시작할 때 저장된 설정 파일을 읽는다.`

### 작업 절차

작업자: 운영자.

1. 설정 파일을 저장하십시오.
2. 서버를 다시 시작하십시오.

### 동작 설명

서버는 시작할 때 저장된 설정 파일을 읽습니다.

동작 설명을 `설정 파일을 읽으십시오`라는 작업 지시로 바꾸지 않는다.
서버 다시 시작과 설정 저장은 예제에서 별도 작업이다.
`설정을 반영하십시오`로 합치면 실제로 해야 하는 행동이 흐려진다.

## 3. 조건의 범위

### 한 행동의 조건

원문: `검증에 실패하면 요청을 거부합니다.`

설명: `검증에 실패하면 시스템이 요청을 거부합니다.`

이 교정은 시스템이 주체라는 문맥이 확인된 경우에만 유효하다.
검증 성공 시의 동작은 원문에 없으므로 추가하지 않는다.

### 여러 행동에 적용되는 조건

원문: `승인을 받은 경우에만 A를 제출한 다음 B를 제출하십시오.`

교정:

`승인을 받은 경우에만 다음 두 단계를 수행하십시오.`

1. A를 제출하십시오.
2. B를 제출하십시오.

조건이 첫 단계에만 적용되는 것처럼 쓰지 않는다.
일회성 조건 확인을 지속적인 감시로 바꾸거나, 지속 조건을 한 번의 확인으로 축소하지 않는다.
승인 상태가 언제 평가되는지가 작업에 중요하고 원문에 없다면 확인한다.

### 필요한 조건과 충분한 조건

`관리자일 때만 실행할 수 있습니다`는 관리자 권한이 필요하다는 뜻이다.
다른 조건이 모두 충족되었다는 뜻은 아니다.
`관리자이면 실행할 수 있습니다`로 바꾸면 다른 조건의 존재 가능성을 지울 수 있다.

### 조건 결합

둘 다 필요한 경우에는 `A와 B를 모두 충족하면`처럼 쓴다.
하나 이상이면 되는 경우에는 `A 또는 B 중 하나 이상을 충족하면`처럼 쓴다.
정확히 하나여야 하는 경우에는 `A와 B 중 하나만 충족하면`처럼 쓴다.
원문이 단순히 `및/또는`로 모호하면 의미를 추측해 하나를 선택하지 않는다.

## 4. 순차 작업과 동시 작업

원문: `버튼을 누른 다음 레버를 당기십시오.`

교정:

1. 버튼을 누르십시오.
2. 레버를 당기십시오.

원문: `버튼을 누른 상태를 유지하면서 레버를 당기십시오.`

교정: `버튼을 누른 상태를 유지하면서 레버를 당기십시오.`

두 번째 문장을 단순한 두 단계로 분리하면 유지 상태가 사라진다.
별도 단계로 나누는 것보다 작업 의미가 우선한다.

## 5. 판정 기준이 없는 작업

원문: `온도가 충분히 낮아지면 덮개를 여십시오.`

대응: 덮개를 열 수 있는 온도 기준이 원문이나 관련 자료에 있는지 확인한다.
기준이 없으면 해당 작업의 확정을 보류한다.
`30°C 이하`처럼 그럴듯한 값을 만들어 넣지 않는다.

원문: `실패하면 몇 차례 다시 시도하십시오.`

대응: 재시도의 위험, 간격, 상한이 실제 작업에 필요한지 확인한다.
정책이 필요한 문서라면 미확정 사항으로 보고한다.
`3회`, `5초 간격`, `지수 백오프`를 일반적인 관행이라는 이유로 추가하지 않는다.

## 6. 경고의 위치와 등급

다음은 제공된 예제 정책이 해당 경고를 요구한다고 가정한 사례다.

원문:

`기존 설정 파일을 삭제하십시오.`

`주의: 설정 파일을 삭제하면 저장된 설정을 복구할 수 없습니다.`

교정:

`주의: 설정 파일을 삭제하면 저장된 설정을 복구할 수 없습니다.`

`기존 설정 파일을 삭제하십시오.`

경고를 해당 행동 앞으로 옮긴다. 이 예제의 경고 내용을 모든 파일 삭제에 일반화하지 않는다.
`주의`를 `위험`으로 바꾸거나, 근거 없이 백업·전원 차단 같은 추가 작업을 지시하지 않는다.
고정된 문구는 표현을 고치지 않고 위치와 적용 범위만 검토한다.

## 7. 실행용 문서와 검토 보고서

실행용 본문에는 확인되지 않은 값이나 빈 명령 인수를 넣지 않는다.
검토 보고서는 본문과 분리한다.

검토 예:

`위치: 3단계.`

`문제: 대기 종료 조건이 없습니다.`

`규칙: KS-06.`

`처리: 종료 조건을 확인하기 전까지 삭제 단계의 확정을 보류합니다.`

이 보고는 작업을 실제로 수행하거나 기술적 안전성을 검증했다는 뜻이 아니다.
