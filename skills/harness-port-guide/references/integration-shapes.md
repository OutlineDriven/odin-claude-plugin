# Integration-shape branches

5. Route to one of three integration shapes by how the bootstrap reaches the model. Shape A is a shell-hook: the harness runs a shell command at session start and reads its stdout. Shape B is an in-process plugin or extension: a JS/TS module with callbacks that run code. Shape C is an instructions-file: an always-on context file the installed extension ships and the manifest declares, with no hook and no code plugin. Shapes compose — the skill-discovery mechanism and the bootstrap mechanism need not be the same shape, but both must still ride the install mechanism. Decide "where are skills discovered?" and "how does the bootstrap reach the model every session?" separately; if more than one install-mechanism surface injects automatically, prefer the most reliable. Done when: the stated action, evidence, and guard all hold.
6. Study the closest reference implementation for the shape being ported end to end before writing; the code is the spec. Done when: the stated action, evidence, and guard all hold.
7. Create the manifest or entry point the harness uses to recognize the plugin, matching existing ones in spirit. Shape A: a plugin manifest with name, version, description, a skills path, and a hooks config registering a session-start hook whose command invokes a polyglot dispatcher. Shape B: the module the harness loads plus the package metadata it needs to be discovered; keep per-harness local install artifacts out of git, but never gitignore the tracked source-of-truth manifest. Shape C: a small manifest with a contextFileName-style field plus the context file itself. Decide how the harness loads the module — whether it runs the source directly or needs a transpile or build step. The framework is zero-runtime-dependency; if the harness actually type-checks or bundles the plugin, an undeclared type import fails, so confirm the approach with the maintainer rather than quietly adding a dependency, and keep any build output out of git. Done when: the stated action, evidence, and guard all hold.
8. Wire the bootstrap injection. The shared goal is to get the bootstrap skill content, wrapped in the framework's important-tags, plus the harness's tool mapping in front of the model at session start, with a note that the skill is already active so the model does not try to load it again. Do not apply one shape's recipe to another. Done when: the stated action, evidence, and guard all hold.
   - Shape A: a script reads the bootstrap SKILL.md (frontmatter included, emitted verbatim), wraps it with the preamble, escapes it, and prints the harness's JSON shape. Get the JSON output shape exactly right — emitting the wrong field or an extra one means the bootstrap never injects or injects twice, because some harnesses read two fields without de-duplicating. Source the exact field, nesting, and event-matcher strings from the harness's hook docs or from a throwaway marker hook that dumps its environment. Match the harness's own event-matcher strings; wrong matchers mean the hook silently never fires. The hook-config schema itself varies per harness, so match the closest existing file rather than a single canonical template. The hook command references a harness-provided plugin-root variable whose name differs per harness; use what the target harness exports.
   - Shape B: read the bootstrap SKILL.md, strip its YAML frontmatter, and assemble the important-tags wrapper plus a short preamble that the skill is already loaded and must not be re-invoked, plus the stripped body, plus the inline tool mapping. If the harness has no skill tool, use the "do not try to load it again" wording, not the "do not use the skill tool" wording. Inject the result as a user-role message, not a system message — system messages bloat tokens when repeated every turn and break some models. Replicate three things: a dedup guard, because the lifecycle callback can fire repeatedly — before injecting, check whether a bootstrap marker is already present and skip if so, and cache the bootstrap content at module level so SKILL.md is not re-read and re-parsed on every call; compaction re-injection, so if the harness compacts history you re-inject afterward, inserting the message after any leading compaction-summary messages; and the per-harness message-object shape, which the harness API exposes — copying a reference's object literal verbatim will fail silently.
   - Shape C: point the extension's context file at the bootstrap and assemble nothing. There is no injector, so do not strip frontmatter or build a wrapped string. The context file the extension ships — declared by the manifest, not the user's own global file — pulls in the bootstrap skill and the tool-mapping reference. If the harness has an include syntax, use it; if not, inline the content into the instructions file. Prove an include is actually expanded with a marker test: a derived harness can accept the syntax yet treat it as a hint the model may choose to read rather than a guaranteed inline expansion, and if the marker is not in context without a tool call, inline the content instead.
9. Write the tool mapping, translating the action vocabulary into the harness's real tools: read a file; create, edit, or delete a file; run a shell command; search file contents or find files by name; fetch a URL or web search; dispatch a subagent, including how to pass the agent type and any config flag needed to enable it; create or update todos; and invoke a skill. Get the real tool names from the harness and never invent them — if the docs do not list them, ask the running model to list the exact machine names of every tool it can call. Confirm how the harness finds the skills directory, because a skills path field is not portable: it may be a manifest skills path field; a co-located skills directory the harness auto-scans where a path field is ignored; an API or registration call; or a staged install dir pairing the manifest with a symlink to the skills, in which case verify the installer dereferences the symlink and copies the real files. Where the mapping lives depends on shape: Shape A in a references file the bootstrap links; Shape B typically inlined into the bootstrap string, and if it is maintained in two places both are updated or the port is half-done; Shape C in a references file pulled into the always-loaded instructions file. Done when: the stated action, evidence, and guard all hold.
10. Handle the skill-invocation mechanism by case. Case 1, a native Skill-style tool: point the mapping at it. Case 2, native skill discovery but no Skill tool: install skills where the harness scans and tell the model to load a skill by reading its SKILL.md with the file-read tool when the skill applies — this is the sanctioned mechanism here, not a violation of the "never read skill files" rule, so say so plainly in the mapping. For the bootstrap itself prefer a declared context file; otherwise fall back to the surfaced skill index, which bootstraps triggering but not the tool mapping and gives no structural guarantee the trigger fires, so the acceptance test is the only guarantee and must run on the model or models users will actually use. Case 3, no skill system at all: the only mechanism is the model reading SKILL.md on demand, but a discovery path must be supplied — either generate a skill index placed inside the important-tags wrapper alongside the tool mapping, which the dedup guard covers but which goes stale as skills are added, or instruct the model to list skills/*/SKILL.md at runtime and read their frontmatter to find a match, which is slower but never stale; prefer the latter. Without either, a no-skill-system port loads the bootstrap but silently never triggers any other skill. Done when: the stated action, evidence, and guard all hold.
11. Skills name actions, not tools. Do not edit skill bodies to fit the harness; porting adds a tool-mapping reference and a bootstrap injector and never reaches into a SKILL.md to swap tool names. The only permitted edit to a skill is a one-line pointer in its platform-adaptation pointer list, which is a convenience pointer rather than behavior-shaping content; do not touch anything else in any skill. Done when: the stated action, evidence, and guard all hold.
12. Everything ships through the harness's own install mechanism; never edit the user's files. The bootstrap, the skills, and the tool mapping all get delivered as part of what the harness installs — a plugin, an extension, a marketplace entry, or an extension-bundled context file. A port must not reach into a user's global or personal config to inject anything. If the install mechanism genuinely cannot carry the bootstrap, that is a limitation to surface, never a license to hand-edit the user's config. A plugin installer may silently strip undeclared files, so make the bootstrap a file the installer recognizes — a manifest-declared context file is the strongest clean bootstrap — never a user-config edit. Done when: the stated action, evidence, and guard all hold.
13. Add tests matching the existing per-harness style. Shape A: assert the hook's stdout has the exact JSON shape the harness consumes and that it contains the bootstrap. Shape B: a unit test that fakes the harness's plugin API and asserts the lifecycle handlers register, the bootstrap injects once, the dedup guard works, and compaction re-injection works, plus an isolated-install integration check. If the bootstrap is cached, test that the cache behaves when the file is missing. These automated tests cover the wiring; the live run in the next step proves the integration actually triggers skills. Done when: the stated action, evidence, and guard all hold.
